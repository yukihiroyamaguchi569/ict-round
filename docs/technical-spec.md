### 3.3 インストールバナー

未インストール環境では、ホーム画面追加を促すバナーを表示します。

- 実装: `src/components/InstallBanner.tsx`、`src/useInstallBanner.ts`、`src/usePwaInstall.ts`
- Android / デスクトップ Chrome では `beforeinstallprompt` を保持し、バナー操作でインストールプロンプトを表示
- iOS Safari では `beforeinstallprompt` が発火しないため、手動追加手順を案内
- 閉じた場合は `localStorage` に記録し、以後表示しない

### 3.4 アプリ本体以外の公開ページ

同一ホスト上に、アプリ本体とは独立した静的ページを配置しています。

| パス | 内容 |
|------|------|
| `/about` | 紹介ページ |
| `/updates` | 更新履歴ページ（`/updates/releases.json` を読み込み） |

これらは React アプリではなく単体の HTML です。ラウンド入力機能は持ちません。外部リソースの読込先は 7.1 を参照してください。

アプリ本体からは、次のリンクで公開ページを新しいタブに開きます。いずれも相対パスで、表示中のタブは移動しません。

| 置き場所 | 表示 | 開くページ |
|----------|------|-----------|
| 開始画面の下部 | 使い方 | 使い方ガイド（`./docs/user-guide/`。取扱説明書の公開ページ） |
| 開始画面の下部 | めぐる君について | 紹介ページ（`./about/`） |
| ラウンド中のヘッダー | `?`（使い方） | 使い方ガイド（`./docs/user-guide/`） |

新しいタブで開くのは、次の理由からです。

- ラウンドの入力内容は、保存するまで画面のメモリ上にしかありません（5.2）。同じタブで別のページへ移ると、保存していない入力が失われます
- ホーム画面から起動したインストール版では、同じ画面で別のページに移るとアプリへ戻る手段がなくなることがあります

### 3.5 統合ページ（`/merge.html`）

複数部署の報告書を 1 本の Word 報告書に統合するためのページです。表を扱うため PC ブラウザでの利用を想定しています。

- 実装: `merge.html`、`src/merge/*`
- アプリ本体（`index.html`）とは別のビルドエントリであり、アプリ本体のバンドルには含まれません（9.2 を参照）
- アプリ本体の開始画面とレポートプレビュー画面から、相対パス `./merge.html` のリンクで遷移します
- 入力は報告書の `.docx`（ラウンドデータを同梱。6.6 を参照）。ファイル選択またはドラッグ＆ドロップで複数件を読み込みます
- **`localStorage` を含む永続化を一切行いません。** 読み込んだデータは JavaScript のメモリ上のみに保持し、再読み込みで失われます
- 出力は統合報告書の `.docx`（6.8 を参照）
- ラウンド入力（評価・写真・総評の記録）機能は持ちません

### 3.6 アプリの紹介（「同僚に紹介する」）

開始画面の「同僚に紹介する」を押すと、紹介先を選ぶダイアログを表示します。ダイアログは紹介文と紹介ページの URL を、利用者が選んだ送り先に渡すだけです。

- 実装: `src/appShare.ts`（紹介文と URL の組み立て）、`src/useAppShare.ts`、`src/components/AppShareDialog.tsx`
- 渡す内容は、アプリに固定で書かれた紹介文と、公開している紹介ページの URL（`https://ict-round.conect.llc/about/`）のみです。**ラウンドの入力データ（担当者名・病棟名・評価・写真・総評）や、チェックリストの内容は渡しません**
- URL は表示中のホストに関係なく、公開環境の紹介ページに固定しています。紹介ページへの訪問を集計できるよう、`utm_source=app_share` と送り先ごとの `utm_medium` を付けます
- 送り先と動作は次のとおりです。いずれも利用者が押したときだけ動作し、ダイアログを開いただけでは何も送りません

| 送り先 | 動作 | `utm_medium` |
|--------|------|--------------|
| メール | `mailto:` で端末のメールアプリを開き、件名と本文（紹介文と URL）を入れる。宛先は空 | `email` |
| LINE | `https://line.me/R/share` を新しいタブで開き、紹介文と URL を渡す | `line` |
| X | `https://x.com/intent/post` を新しいタブで開き、短い紹介文と URL を渡す | `x` |
| リンクをコピー | Clipboard API で URL をクリップボードに書き込む。書き込めない場合は URL を画面に表示し、利用者が手で選択できるようにする | `copy` |
| その他のアプリ | Web Share API（`navigator.share`）で OS の共有画面を開く。対応する端末でのみ表示 | `share` |

- LINE と X へは、利用者が押したときに限り、上記の紹介文と公開 URL だけをクエリ文字列で渡します。外部サービスへのリンクには `rel="noopener noreferrer"` を付け、遷移元の URL を送りません
- メールの送信、LINE・X への投稿は、遷移先のアプリやサービスで利用者自身が行います。本アプリが送信や投稿をすることはありません

### 3.7 お問い合わせフォームへのリンク（「ご意見・ご要望」）

質問や改善の要望を受け付けるため、運営者の Google フォーム（お問い合わせフォーム）へのリンクを置いています。

- 実装: `src/feedback.ts`（URL の組み立てと端末の判定）、`src/components/FeedbackLink.tsx`
- 置き場所は次の 2 か所です
  - 開始画面の下部のリンク列の最後（「ご意見・ご要望」）。リンクが 1 行に収まらない幅では折り返します
  - 報告書の画面（6.6）で、共有が完了した後またはファイル保存を実行した後に表示する「使ってみた感想を送る」。共有をキャンセルした場合は表示しません。サンプルのラウンドでも表示します
- どちらも `target="_blank"` と `rel="noopener"` を付けた通常のリンクで、フォームを新しいタブで開きます。保存していないラウンドの入力が、画面の遷移で失われないようにするためです
- フォームの URL（`https://docs.google.com/forms/d/e/…/viewform`）に、Google フォームの事前入力の仕組み（`usp=pp_url` と `entry.<番号>`）で次の 2 項目だけを付けます。値は `encodeURIComponent` でエンコードします

| 項目 | 値 |
|------|-----|
| アプリのバージョン | ビルド時に埋め込んだ `package.json` の `version` |
| 端末の種類 | `iPhone` / `iPad` / `Android` / `パソコン` / `その他` のいずれか（フォームの選択肢と同じ文字列） |

- 端末の種類は、User-Agent と `navigator.maxTouchPoints` から次の順で判定します。iPadOS の Safari は既定で Mac の User-Agent を送るため、`Macintosh` でタッチ点が 2 以上のものを iPad とみなします
  1. `iPhone` を含む → `iPhone`
  2. `iPad` を含む、または `Macintosh` を含みタッチ点が 2 以上 → `iPad`
  3. `Android` を含む → `Android`（タブレットを含む）
  4. `Windows`・`Macintosh`・`CrOS`・`Linux` のいずれかを含む → `パソコン`
  5. 上記以外 → `その他`
- **ラウンドの入力データ（担当者名・病棟名・評価・写真・総評・コメント）や、チェックリストの内容は URL に含めません**
- リンクを押すと、事前入力の 2 項目を含む URL でフォームの画面を開きます（このとき URL は Google に届きます）。回答として送信するかどうかは、利用者がフォームの画面で決めます。送信した内容は Google のサービス上で処理され、運営者が受け取ります

### 4.3 部署間の受け渡し形式

## 5. 永続化仕様

### 5.1 `localStorage` キー

| キー | 内容 |
|------|------|
| `icn-round:checklist-library` | 保存済みチェックリスト一覧 |
| `icn-round:active-checklist-id` | 選択中チェックリスト ID |
| `icn-round:saved-rounds` | 保存済みラウンド一覧（担当者名・病棟名・評価・写真・総評を含む） |
| `icn-round-theme` | テーマ設定 |
| `icn-round-icon` | アイコン設定 |
| `pwa_install_tracked` | インストール計測の重複送信防止フラグ |
| `pwa_banner_dismissed` | インストールバナーを閉じたかどうか |
| `icn-round:last-seen-version` | 新機能のお知らせを最後に確認したアプリのバージョン |
| `icn-round:round-used` | 通常のラウンド（サンプル以外）を保存、または報告書を出力したことがあるか（値は `1`。開始画面の「サンプルデータで試す」の出し分けに使う。6.1.1 を参照） |

`IndexedDB`、`Cookie`、`sessionStorage` はアプリ本体では使用していません。Cookie は Google Analytics 4 が設定します（7.4 を参照）。

### 5.2 保存方針

- 入力中ラウンドは React state 上に保持
- `保存` 操作時のみ `SavedRound` を `localStorage` に保存
- チェックリストライブラリは追加 / 削除時に都度保存
- テーマ、アイコン、選択中チェックリストは変更時に保存

### 5.3 保存形式と暗号化

- 保存形式は `JSON.stringify()` による**平文**の JSON 文字列です
- 写真は Base64 の `dataUrl` として、同じく平文で JSON 内に格納します
- **アプリ独自の暗号化は実装していません**
- 端末紛失時の情報保護は、OS のストレージ暗号化（iOS のデータ保護、Android の File-Based Encryption、BitLocker、FileVault 等）と画面ロックに依存する設計です
- したがって、端末に画面ロックとストレージ暗号化を設定した上での運用を前提とします

#### 暗号化を実装していない理由

本アプリはバックエンドを持たないため、暗号鍵の保管場所が JavaScript のバンドル内しかありません。バンドルは誰でも取得して内容を確認できるため、鍵を同梱した暗号化は次のいずれの脅威にも効果がありません。

| 脅威 | バンドルに鍵を同梱した暗号化の効果 |
|------|--------------------------------|
| 端末の紛失・盗難 | 効果なし（OS のストレージ暗号化と画面ロックが防御にあたる） |
| 共用端末で他者がアプリを開く | 効果なし（アプリが自動的に復号するため素通りする） |
| XSS・悪意のあるブラウザ拡張 | 効果なし（同一コンテキストから鍵を参照できる） |
| ストレージの物理的な解析 | 効果なし（鍵が公開されているため。OS 暗号化が防御にあたる） |

実効性を持たせるには利用者ごとのパスフレーズ入力と鍵導出（PBKDF2 等）が必要ですが、起動のたびに入力が発生すること、失念時に復号不能となりデータを失うことから、ラウンド業務での可用性を著しく損ないます。

以上より、保存データの機密性は**端末側の管理策（画面ロック、ストレージ暗号化、MDM）で担保する**方針としています。施設の要件として利用者認証つきの暗号化が必要な場合は、別途ご相談ください。

#### 併用を推奨する運用上の対策

暗号化の有無にかかわらず、端末内に記録が残り続けること自体が主要なリスクです。次の運用を推奨します。

- 端末に画面ロックとストレージ暗号化を設定する
- レポート出力後、保存済みラウンドをアプリ内で削除する
- 共用端末では使用後にブラウザのサイトデータを削除する
- 可能であれば MDM 管理下の端末で利用する

## 6. 機能仕様

### 6.1 ラウンド開始

- 担当者名は必須
- 病棟名は任意
- 担当者名の初期値は、直前に利用者が入力した担当者名（連続して別病棟を回る場合の再入力を省くため）。病棟名は毎回空にする
- この引き継ぎ値は React state のみで保持し、単独では永続化しないため再読み込みで空に戻る。保存済みラウンドを開いても引き継ぎ値は変化しない
- 開始時刻は `new Date().toLocaleString('ja-JP')` で生成
- 選択中チェックリストに基づき `checklistResults` を初期化
- アプリ更新後の初回表示時は、未確認の更新内容を「新機能のお知らせ」ダイアログとして開始画面に重ねて表示する。確認済みのバージョンは `localStorage`（`icn-round:last-seen-version`）に記録し、記録が現在のバージョン以上なら更新履歴を取得しない。それ以外の場合は起動時に配信元ホストから `/updates/releases.json` を取得し、記録より新しい（現在のバージョン以下の）エントリを新しい順に表示する。記録がない端末では最新の 1 件のみ表示する。閉じると、表示した中で最新のバージョンを記録する。記録より古いバージョンで上書きはしない。取得に失敗した場合（通信エラー、HTTP エラー、5 秒のタイムアウト、不正な JSON）や未確認のエントリが 0 件の場合はダイアログを表示せず、記録も変更しない。オフライン時は Service Worker がキャッシュした更新履歴が使われることがある（実装: `src/whatsNew.ts`、`src/components/WhatsNewDialog.tsx`）

### 6.1.1 サンプルデータで試す

初めて使う利用者が、入力済みのサンプルで報告書の出力までを試すための機能です（実装: `src/sampleRound.ts`、`src/samplePhotos.ts`、`src/useSampleStart.ts`、`src/useRound.ts`）。

- 開始画面に「サンプルデータで試す」を表示する。この端末で通常のラウンドを保存したことも報告書を出力したこともなく、保存済みラウンドが 0 件のときは開始フォームの下に目立つ形で、それ以外は画面下部のリンク列に表示する
- 通常のラウンドの保存に成功したとき、または報告書の共有が完了したとき・ダウンロードしたときに、`localStorage` の `icn-round:round-used` に記録する（5.1）。サンプルのラウンドでは記録しない。記録は消さないため、保存済みラウンドを削除しても目立つ形には戻らない。`localStorage` を読み書きできない場合は記録なしとして扱う。開始画面を表示するたびに読み直すため、ラウンドから戻ったときに反映される（実装: `src/roundUsage.ts`）
- サンプルは、選択中のチェックリストにかかわらず標準チェックリスト（`CHECKLIST_CATEGORIES`）を使う。全項目に固定の評価（A / B / C）を入れ、固定の総評、担当者「サンプル 太郎」、病棟名「【サンプル】3階東病棟」を設定する
- 写真は、アプリに同梱した 3 枚（`/sample/item-1.jpg`、`/sample/item-2.jpg`、`/sample/general-1.jpg`）を開始時に配信元ホストから取得し、data URL にして使う。`item-1` は項目 `hand-hygiene-2`、`item-2` は項目 `linen-2` に紐づけ、`general-1` は全体写真とする。取得は 1 枚ごとに、ダウンロードと画像の読み込みを合わせて 8 秒でタイムアウトし、取得できなかった写真（通信エラー、HTTP エラー、JPEG 以外の応答、画像として読み込めないもの）は外してサンプルを開始する
- サンプルのラウンドは保存しない。保存ボタンを表示せず、トップ画面に戻るときの保存確認も出さない。担当者名を画面上で変えても、次回の開始画面に引き継ぐ担当者名は変えない
- サンプルかどうかは画面の状態（React state）でのみ保持する。`RoundData`（4.2）と `.docx` に同梱する `RoundExport`（4.3）の形式は通常のラウンドと同じで、病棟名の【サンプル】で区別できる
- 写真の取得中に通常のラウンドを開始した場合や保存済みラウンド一覧へ移った場合は、取得が終わってもサンプルを開かない

- 各項目に `A` `B` `C` `null` を設定
- 進捗は `rating !== null` の件数から算出
- カテゴリアコーディオンは先頭カテゴリのみ初期展開

### 6.3 チェックリスト取り込み

- 対応形式: `.csv` `.xlsx`
- CSV は独自パーサで 2 列を解析
- Excel は `read-excel-file` ライブラリで先頭シートのみ読込
- カテゴリ名か点検項目のどちらかが空の行は読み飛ばす（空行や、1 列目だけのタイトル行を含む）
- 最初のデータ行より前にある、1 列目が `category`（大文字小文字と前後の空白は区別しない）の行は見出し行としてスキップする。先頭に空行やタイトル行があっても見出し行として扱う。データ行より後に現れた場合はカテゴリ名として取り込む
- 同一カテゴリ名は自動グルーピング
- 項目 ID は「カテゴリ名から作る接頭辞-カテゴリ内の連番」とする。接頭辞はカテゴリ名を小文字化し、空白を `-` に置き換え、英数字・`_`・`-`・日本語以外の文字を除いて先頭 20 文字に切り詰めたもの。大文字小文字や記号だけが違うカテゴリ、先頭 20 文字が同じカテゴリでは接頭辞が重なるため、後から現れたカテゴリの接頭辞を `接頭辞~2`、`接頭辞~3` …（使われていない最小の番号）にずらして項目 ID の重複を避ける。`~` は接頭辞の生成で必ず除かれる文字なので、ずらした ID がほかのカテゴリの ID と重なることはない。接頭辞が重ならないファイルでは ID はずらさず、同じファイルからは常に同じ ID ができる。取り込み済みのチェックリストは ID ごと保存されているため、この規則の影響を受けない
- 取り込み後は新規 `SavedChecklist` として保存

### 6.3.1 チェックリストの作成・複製（エディタ）

- 開始画面から全画面のエディタを開き、カテゴリと点検項目の追加・編集・削除、↑↓ ボタンによる並べ替えを行う
- 起点は「空のチェックリスト（カテゴリ 1・項目 1）」または「既存チェックリストの複製（名前の初期値は『〇〇のコピー』）」の 2 通り
- 保存結果は常に新規 `SavedChecklist` としてライブラリ（`localStorage`）に追加し、選択状態にする。既存のチェックリストは書き換えない。保存済みラウンドは項目 ID で評価や写真を項目に結び付けているため、既存の項目定義を変えないことで保存済みラウンドへの影響を避けている
- 保存時の変換（実装: `src/checklistEditor.ts`）
  - 名前・カテゴリ名・項目の前後の空白を除去し、空の項目と項目のないカテゴリを除外する
  - 名前が空、有効な項目が 0 件、項目のあるカテゴリの名前が空、同名カテゴリの重複のいずれかがあれば保存せずエラーを表示する
  - 各項目の `category` は所属カテゴリの名前に揃える
  - 複製元の項目 ID を引き継ぐのは、保存するカテゴリ名と項目の文言（前後の空白を除いたもの）が、複製元のカテゴリ名・文言と文字列として完全に一致する項目だけとする。統合（6.8）が行を文字列のまま比較するのに合わせ、複製元のカテゴリ名や文言に前後の空白がある項目も新しい項目として扱う。同じ ID が別の文言を指すことを避けるため、カテゴリ名か文言のどちらかを変えた項目（誤字の修正やカテゴリ名の変更を含む）は新しい項目として扱う
  - 新規の項目と上記で ID を引き継がない項目には `item-` で始まるランダムな ID を振る。新しい ID は、引き継いだ ID とも、文言を変えたり空にしたりした項目の複製元 ID とも重ならないようにする。引き継ぐ ID が重複した場合は 2 件目以降に新しい ID を振る

この ID の振り方は、複数部署の報告書の統合（6.8）とも関係します。統合では行を「項目 ID ＋ カテゴリ名 ＋ 項目の文言」で識別し、同じ項目 ID に別の項目が割り当てられていると、行を分けたうえで警告を表示します。エディタで複製・編集したチェックリストでは、カテゴリ名と文言が複製元と同じ項目だけが複製元の ID を引き継ぎ、文言かカテゴリ名を変えた項目には新しい ID を振ります。空にして削除した項目の ID も、新しく振る ID には使いません。そのため、複製元のチェックリストで記録した報告書と、複製・編集したチェックリストで記録した報告書を統合しても、変更していない項目は同じ行にまとまり、同じ ID が別の文言を指すことによる行の食い違いと警告を避けられます。なお、片方にしかない項目がある場合の警告（6.8）は、この ID の振り方とは別に表示されます。

#### 表のテキストの貼り付け

- エディタの名前欄の下にある「表のテキストを貼り付けて読み込む」から、エディタ内の折りたたみのセクションとしてテキスト欄を開く。貼り付けたテキストを入力のたびに振り分け、カテゴリ数・項目数とカテゴリごとの項目を表示する。「読み込む」で、下書きが作成直後の空の状態（名前が空で、名前の空のカテゴリ 1 つに空の項目 1 つ）なら下書きのカテゴリを置き換え、そうでなければ末尾に加える。保存時の変換と検証は上記と同じ
- 紙の表からの文字認識は OS の機能（iPhone・iPad のテキスト認識表示、Android の Google レンズなど）で利用者が行い、アプリは認識結果のテキストをクリップボード経由で受け取るだけとする。アプリは画像を扱わず、テキストも端末の外へ送信しない。文字認識での画像の扱い（端末内で処理するか、提供元のサーバーへ送るか）は OS や利用するアプリの仕様による
- 振り分け（実装: `src/checklistText.ts`）
  - タブを含む行があれば表（Excel・Word からのコピー）として読む。各行の 1 列目をカテゴリ、2 列目を項目とし、3 列目以降は捨てる。先頭の列は、空の行を除くどの行にも互いに異なる数字だけが入り、後ろにカテゴリと項目の列が続く（2 列目が文として終わらず、3 列目が評価や空欄だけではない）場合に、番号の列として除く。連番のカテゴリに項目が 1 つずつあり 3 列目が備考の表は、番号付きの表と区別できないことがある。Excel が引用符で囲んだセルの中の改行とタブでは、行やセルを分けない。カテゴリの欄が空の行は直前のカテゴリを引き継ぐ（セル結合への対応）。見出しのセル（ジャンル・カテゴリ・チェック項目・評価など）を含む行は捨てる
  - タブがなければ行ごとに読む。見出しだけの行、評価だけの行（A・B・C・○・× など）、ページ番号だけの行は捨て、行末の評価は外す（空白や句点の後の評価に加え、日本語の文字に続く A・B・C・○・× なども、残りが文として終わる場合に外す。「病棟A」のような名前は変えない）。行頭が ■ □ ● ◆ ◇ 【 # の行はカテゴリとする。このような記号の付いた行が 1 行でもあれば、利用者がカテゴリを指定したものとみなし、ほかの行（表として読む場合のタブのない行を含む）はすべて項目とする。記号の付いた行がなければ、見出し番号（「1.」「(1)」「①」など）で始まる行は文末が句点や述語（「いる」「ない」など）でなければカテゴリとする。「短い語 ＋ 空白 ＋ 文」の行は最初の語をカテゴリ、残りを項目とする。それ以外は 15 文字以下で文末が句点や述語でない行をカテゴリ、ほかを項目とする
  - 同じ名前のカテゴリは 1 つにまとめる。項目のないカテゴリも結果に残し、プレビューに「項目なし」と表示する（短い項目がカテゴリと推測されたときに、黙って消えないようにするため。保存時には省かれる）。カテゴリより前の項目は名前が空のカテゴリに入れ、保存時の検証で名前の入力を促す

### 6.6 レポートプレビュー / 出力

- 総評が空（空白のみの場合を含む）のときは、総評の見出しに続けて書き加えられるよう空の段落を 1 つ置きます
- サンプルのラウンド（6.1.1）では、プレビューと `.docx` の表題、および共有時の件名を「【サンプル】感染対策ラウンド報告書」とします
- 生成した `.docx` に、`RoundExport`（4.3）を JSON 文字列として **customXml パート**（`customXml/itemN.xml`、名前空間 `urn:meguru-round:export`）として書き込みます。統合ページはこのパートを読み取ります
  - 実装: `src/roundExportDocx.ts`。`[Content_Types].xml` と `word/_rels/document.xml.rels` を併せて更新し、Word が開いても壊れない正規の形で格納します
  - 報告書としての体裁・本文は変わりません。共有するファイルは `.docx` 1 本のみで、別途 JSON 等を出力・共有する仕組みはありません
- 共有可能端末では `navigator.share({ files })` を優先。iOS で共有画面が即閉じるのを避けるため、`.docx` はプレビュー表示時に事前生成しておき、操作時は同期的に共有します
- 共有非対応時、および共有に失敗した場合は `file-saver` によりダウンロード
- 事前生成に失敗した場合は、その理由を画面に表示します（共有・出力ボタンは押せないままとなるため）
- 共有が完了した後、またはファイル保存を実行した後に、お問い合わせフォームへのリンク「使ってみた感想を送る」を表示します（3.7）
- ファイル名形式:
  - `ICTround_<YYYY-MM-DD>_<英数4文字>.docx`
  - 日付は出力した端末のローカル日付です（UTC ではありません）。日付は報告書のプレビューを開いたときに決まり、共有時に添える本文（`<担当者名> - <YYYY-MM-DD>`）にもファイル名と同じ日付を使います
  - 日本語名では AirDrop の転送が失敗するため半角英数のみとし、複数人分の受信時に衝突しないよう末尾に乱数 4 文字を付けます

### 6.8 複数部署の報告書の統合

統合ページ（3.5）の機能です。サーバーを介さず、利用者が集めたファイルをブラウザ内で処理します。

- 入力は報告書の `.docx`。先頭バイトで ZIP かどうかを判定し、customXml パートから `RoundExport` を取り出します。ZIP でないファイルは、その旨をファイル単位のエラーとして表示します
- 1 ファイル 50MB を超えるファイルは、ブラウザが応答しなくなるのを避けるため読み込み前に拒否します
  - customXml パートが見つからない場合は、その旨をファイル単位のエラーとして表示します（Word で開いて保存し直すと失われることがあるため）
- 行の並びは、読み込んだ全ファイルのチェック項目の和集合。列の並びは読み込み順（同じ病棟名の報告書は最初に現れた位置に 1 列としてまとまる）で、画面上で入れ替えられます
- 行の同一性は「項目 ID ＋ カテゴリ名 ＋ 項目の文言」で判定します。項目 ID は「カテゴリ名-連番」で機械生成されるため、別々に編集したチェックリストでは同じ ID が別の項目に割り当たり得ます。同じ ID でも文言が違う場合は別の行として出力し、1 つの報告書の中で項目 ID が重複していなければ、各部署の評価をその部署の文言の行に載せます。1 つの報告書の中で同じ ID が複数の項目に使われている場合は、評価がどの項目のものか判別できないため、その報告書の評価は最初に現れた項目の行にだけ載せます。同じ ID の残りの行は、同じ病棟の別の報告書がその行を評価していればその評価で埋まり、どの報告書も評価していなければ `—` となります
- 列の同一性は病棟名で判定します（前後の空白を除いた完全一致。表記ゆれの正規化は行いません）。病棟名が同じ報告書は 1 列にまとめ、列見出しは病棟名のみとします。病棟名が未入力の報告書はまとめず、担当者名を列見出しとする 1 ファイル 1 列とし、それでも見出しが重なる場合は連番を付けます
- 1 列にまとまった報告書の実施日時は、その列で最も早い日時を採ります
- 同じ列（同じ病棟）の同じ行に複数の評価が集まった場合は 1 つの値に集約します。未評価（`null`）は他の担当者の評価で補完し、評価が食い違う場合は厳しい方（`C` ＞ `B` ＞ `A`）を採用します。1 つの病棟をチェック項目で分担して複数名で回る使い方を想定した集約であり、病棟が違う列どうしの評価は集約しません（食い違いではなく別々の結果であるため）
- 列がその項目を持つかどうかは、報告書に同梱されたチェックリスト定義（`categories`）で判定します。チェック結果の記録があるかどうかでは判定しないため、定義にある項目は結果が無くても未評価として扱います
- セルが `—` になるのは、その列（病棟）のどの報告書にも該当の項目が無い場合と、項目はあるが担当者全員が未評価の場合です。加えて、1 つの報告書の中で項目 ID が重複している場合、最初に現れた項目以外の行は、同じ病棟の別の報告書がその行を評価していなければ `—` になります
- 次の場合は画面に警告を表示します（出力は継続します）
  - 他の列にある項目を持たない列（病棟）がある。判定は列単位なので、同じ病棟の担当者が項目を分担していれば、個々の報告書に無い項目でも警告や `—` にはなりません
  - 同じ項目 ID に別のチェック項目が割り当てられている（別々に作ったチェックリストが混在している場合。同じ項目のつもりでも行が分かれるため）
  - 1 つの報告書の中で同じ項目 ID が複数のチェック項目に使われている（該当する報告書と項目 ID を示します。評価と写真は項目 ID で記録するため、評価は最初に現れた項目の行にのみ載り、写真は重複したり別の項目名の下に出ることがあります）
  - チェックリスト定義に無い項目 ID の評価が報告書に含まれている（該当する報告書と項目 ID を示します。載せる行が無いため表には反映されません）
  - 同じ病棟の同じ項目に違う評価が付いている（列ごとに 1 件へまとめ、項目の文言と担当者ごとの評価を示します。採用したのは厳しい方の評価です）
  - チェックリスト名が混在している
  - 列（病棟）数が 15 件を超え、部署の列が狭くなって読みにくくなる
- 出力は `docx` ライブラリで生成する A4 横向きの `.docx`。評価マトリクスに続けて、病棟ごとの総評と写真を出力します。1 つの列に複数の報告書がある場合は、1 つの見出しの下に担当者名を添えて総評を並べ、写真もその節にまとめます。総評が空の報告書は段落を出しません。総評の節見出しと病棟の見出しは常に出力し、どの報告書にも総評が無い病棟には書き加えられるよう空の段落を 1 つ置きます
- 表は固定レイアウトのため、列幅は本文幅（A4 横の 13,958 twips）に収まるよう部署数から計算します。チェック項目列に最低幅を残し、残りを部署数で等分するため、部署が増えるほど部署の列は狭くなります
- `.docx` の生成に失敗した場合は、その理由を「Word出力」ボタンの近くに表示します。読み込みエラーの欄とは分けて表示し、次に出力を始めた時点で消します
- ファイル名形式:
  - `ICTround_merged_<YYYY-MM-DD>.docx`
  - 日付は出力した端末のローカル日付です（UTC ではありません）

| `www.google-analytics.com` | アクセス解析イベントの送信（7.4） | なし |

**利用者の操作で開く外部サービス:** 次の場合に限り、外部サービスのページを新しいタブで開きます。アプリが自動で外部サービスへ接続することはありません。

| 開く先 | 開くとき | URL で渡す内容 | ラウンド入力データ |
|--------|----------|----------------|--------------------|
| `line.me` / `x.com` | 開始画面の「同僚に紹介する」で利用者が LINE または X を押した場合（3.6） | アプリに固定で書かれた紹介文と、公開している紹介ページの URL | なし |
| `docs.google.com`（お問い合わせフォーム） | 開始画面の「ご意見・ご要望」、または報告書の出力後に表示する「使ってみた感想を送る」を利用者が押した場合（3.7） | アプリのバージョンと端末の種類（フォームの事前入力） | なし |

紹介ページ `/about` と更新履歴ページ `/updates` は、上記に加えて以下を読み込みます。これらのページにラウンド入力機能はありません。

| 通信先 | 用途 |
|--------|------|
| `cdn.tailwindcss.com` | Tailwind CSS（CDN 版） |
| `api.qrserver.com` | アプリ URL の QR コード画像生成（`/about` のみ） |

統合ページ `/merge.html` から発生する通信は、配信元ホスト（HTML / JS / CSS）と Google Fonts（`fonts.googleapis.com` / `fonts.gstatic.com`）のみです。アクセス解析（gtag.js）は読み込まず、Service Worker も登録しません。**読み込んだ報告書ファイルの内容を外部へ送信する処理はありません。**

`/about` には同じお問い合わせフォームへのリンク（`forms.gle`）を設置していますが、これはページ読込時に通信するリソースではなく、**利用者がリンクを押して遷移した場合にのみ**通信が発生する外部サイトです。フォームへ入力した内容は Google のサービス上で処理されます。

### 7.2 Service Worker

`index.html` で `./sw.js` を登録します。

キャッシュ戦略は以下です。

- アプリシェル: インストール時に事前キャッシュ（サンプルの写真 3 枚を含む。オフラインでもサンプルを写真付きで開始できるようにするため）
- Google Fonts: Cache First
- ナビゲーション: Network First
- 同一オリジンの `/assets/`: Cache First
- その他の同一オリジン GET: Network First

### 7.3 オフライン動作

- 初回アクセス後は、キャッシュ済みアセット範囲で再訪可能
- ただし外部フォント未取得時は代替フォント表示となる可能性あり
- サーバーを介したラウンドデータの同期・共有の仕組みは持たない。部署間の受け渡しは、利用者自身がファイル（`.docx`）を渡し、統合ページで読み込む形のみ（6.8）
- gtag.js はオフライン時のイベント再送を行わないため、圏外で発生した解析イベントは復旧後も送信されず欠測する

### 7.4 アクセス解析（Google Analytics 4）

#### 7.4.1 構成

- 実装: `src/analytics.ts`
- 測定 ID はビルド時の環境変数 `VITE_GA4_MEASUREMENT_ID` から埋め込みます
- 環境変数が未設定のビルドでは、アプリ本体と公開文書（`/docs/*`）は gtag.js を読み込まず、解析は一切動作しません（アプリ本体では `initAnalytics()` が即 return）
- 公開環境では GitHub Actions のシークレット経由で測定 ID を設定しています（`.github/workflows/deploy.yml`）
- gtag.js は本番のホスト（`ict-round.conect.llc`）で開いたときにだけ読み込みます。ホスト名は完全一致で判定します。プレビュー環境や手元で動かす本番ビルド（`npm run preview` など）では読み込まず、解析イベントを送信しません。例外として、アプリ本体は開発サーバー（`npm run dev`）でも、動作確認のため DebugView を有効にして読み込みます
- `/about` と `/updates` は React アプリとは独立に、測定 ID を含む gtag を HTML 内へ直接記述しています。公開文書（`/docs/*`）にはビルド時に同じ形で埋め込みます。これらのページは開発サーバーを含め、本番のホスト以外では gtag.js を読み込みません
- 統合ページ（`/merge.html`）では gtag を読み込まず、解析は動作しません

#### 7.4.2 送信するイベント

| イベント | 送信契機 | パラメータ |
|----------|----------|-----------|
| `page_view` | 初回表示時（SPA のため実質1回） | gtag 標準項目 |
| `pwa_install` | インストール検知時 | `method`（`appinstalled` / `standalone_first_launch`） |
| `pwa_install_banner_click` | インストールバナーの操作 | `method` |
| `pwa_install_prompt_result` | インストールプロンプトの結果 | `outcome` |
| `pwa_install_banner_dismiss` | バナーを閉じた時 | `method` |
| `photo_add_attempt` | 写真追加画面で「撮影」または「ギャラリーから選択」を押した時 | `method`（`camera` / `gallery`） |
| `photo_add_success` | 選択した写真の読み込みに成功した時 | `method`（`camera` / `gallery`）、`photo_age`（ファイルの最終更新時刻から選択時までの経過時間の区分。1 分以内 `under_1m` / 10 分以内 `1m_10m` / それより前 `over_10m`。端末の時計のずれで未来の時刻になった場合は `under_1m`。時刻そのものは送信しない。ブラウザによってはギャラリーから選んだファイルの最終更新時刻が選択した時刻になるため、撮影時期を正確に表す値ではなく、`method` と組み合わせて傾向を見るための値） |
| `photo_add_failure` | 写真の追加が完了しなかった時。1 回の `photo_add_attempt` に対し、`photo_add_success` と合わせて最大 1 回 | `method`（`camera` / `gallery`）、`reason`（ファイルが 10MB を超えた `too_large` / 写真の読み込み・縮小に失敗した `compress_error` / 選択画面やカメラを閉じた `cancelled`。`cancelled` はファイル選択の `cancel` イベントに対応したブラウザでのみ送信） |
| `checklist_import_open` | チェックリスト取り込みダイアログを開いた時 | なし |
| `checklist_import_error` | 取り込むファイルの読み込みに失敗した時 | `file_type`（`csv` / `xlsx`） |
| `checklist_import_success` | 取り込んだチェックリストを保存した時 | `file_type`（`csv` / `xlsx`） |
| `checklist_editor_open` | チェックリストのエディタを開いた時 | `source`（`new` / `copy`） |
| `checklist_editor_save` | エディタで作成したチェックリストを保存した時 | なし |
| `checklist_text_import` | エディタで貼り付けた表のテキストを「読み込む」で下書きに入れた時 | `format`（タブ区切りの表 `table` / 行ごとのテキスト `lines`） |
| `round_start` | ラウンドを新しく開始した時（サンプルを含む。保存済みラウンドを開いた時は送信しない） | `sample`（サンプルなら `true`、通常のラウンドなら `false`） |
| `round_export` | 報告書の共有が完了した時、またはファイル保存を実行した時（共有をキャンセルした場合は送信しない） | `method`（`share` / `download`）、`sample`（`true` / `false`） |
| `help_open` | 「使い方」を押した時 | `from`（開始画面 `start` / ラウンド中のヘッダー `round`） |
| `about_link_click` | 開始画面の「めぐる君について」を押した時 | なし |
| `app_share` | 「同僚に紹介する」のダイアログで、メール・LINE・X を押した時、リンクのコピーに成功した時、その他のアプリの共有が完了した時（共有をキャンセルした場合は送信しない） | `method`（`email` / `line` / `x` / `copy` / `share`） |
| `feedback_open` | お問い合わせフォームへのリンクを押した時（3.7） | `from`（開始画面の「ご意見・ご要望」 `start` / 報告書の画面の「使ってみた感想を送る」 `report`） |

写真の追加・チェックリストの取り込みと作成・ラウンドの開始・報告書の出力・使い方の表示・アプリの紹介・お問い合わせフォームを開く操作に関するイベントは、操作の種類と押した場所、貼り付けたテキストの形式（表か行ごとか）、サンプルかどうか、写真の新しさの区分、写真の追加が完了しなかった理由の種類だけを送信します。写真、撮影日時、ファイル名、ファイルサイズ、チェックリストの内容や件数、貼り付けたテキスト、エラーメッセージは含みません。

上記に加え、GA4 が自動収集する `session_start`、`first_visit`、`user_engagement` が送信されます。
ユーザープロパティとして `display_mode`（`standalone` / `browser`）を設定します。

#### 7.4.3 送信しないもの

以下は GA4 へ**一切送信しません**。送信する実装が存在しません。

- 担当者名
- 病棟名
- チェックリストの評価結果
- 写真
- 総評
- 取り込んだチェックリストの内容
- 作成画面に貼り付けたテキスト
- 保存済みラウンド

アプリは SPA であり、URL に入力値を含めないため、`page_view` の URL 経由で入力内容が送信されることもありません。

#### 7.4.4 GA4 側で取得される標準情報

gtag.js の標準動作として、以下が Google に送信・記録されます。

- IP アドレス（GA4 では地域推定に使用後、レポートには保持されない）
- User-Agent（端末種別・OS・ブラウザ）
- 参照元 URL、閲覧ページの URL とタイトル
- `_ga` Cookie による匿名の識別子（`client_id`）

データ保持期間は GA4 の設定で 14 ヶ月としています。

#### 7.4.5 エラーログ収集

Sentry 等のエラー監視サービスは導入していません。例外情報を外部へ送信する実装はありません。

### 7.5 音声入力について

**本アプリに音声入力機能はありません。** マイクを使用せず、音声データを扱う実装も持ちません。

- v1.7.5 までは総評タブに `SpeechRecognition` を用いた音声入力を実装していましたが、端末本体の音声入力機能で代替できるため **v1.7.6（2026年7月2日）で削除**しました
- 現在アプリがマイクへのアクセス許可を要求することはありません

なお、利用者が端末キーボードの音声入力（iOS の音声入力、Android の音声認識など）を用いて総評を入力することは可能です。この場合の音声データの扱いは**端末 OS の機能に属し、本アプリの管理外**です。OS の実装によっては音声が OS 提供元のサーバーへ送信されて認識されるため、利用可否は各施設のポリシーに従って判断してください。

## 8. セキュリティ・個人情報

### 8.1 取り扱うデータ

- 担当者名
- 病棟名
- チェック結果
- 写真
- 総評

これらはすべて利用端末内にとどまります。バックエンドが存在しないため、サーバー側に保管される複製はありません。

ただし、担当者が共有・保存する報告書 `.docx` には、統合機能のためにラウンドデータ（担当者名・病棟名・評価・写真・総評）が機械可読な形で同梱されます（6.6）。統合ページが出力する統合報告書には同梱されません。ファイルを渡した相手には、報告書の記載内容とあわせてこのデータも渡ることになります。端末外へ持ち出したファイルの管理は利用施設の運用に委ねられます。

### 8.2 外部送信

- **ラウンド内容（担当者名・病棟名・評価・写真・総評）を外部へ送信する処理は実装していません**
- アプリが自動で行う外部通信は、静的ファイル取得、フォント取得、アクセス解析の3種類です（7.1）。このほか、利用者が「同僚に紹介する」で LINE・X を押した場合、お問い合わせフォームへのリンクを押した場合に限り、そのサービスのページを開きます（7.1、3.6、3.7）
- アクセス解析では、入力データを含まない利用状況イベントのみを送信します（7.4）
- 「同僚に紹介する」は、利用者が送り先を押したときだけ、固定の紹介文と公開 URL を送り先（メールアプリ、LINE、X、クリップボード、OS の共有画面）へ渡します。ラウンドのデータは渡しません（3.6）
- お問い合わせフォームへのリンクは、アプリのバージョンと端末の種類だけを事前入力として URL に付けます。ラウンドのデータは渡しません。回答の送信は利用者がフォームの画面で行います（3.7）
- エラーログ収集サービスは導入していません
- マイクを使用する機能はありません（7.5）

### 8.3 保存データの暗号化

- 端末内の保存は平文の JSON です。アプリ独自の暗号化は行いません
- バックエンドを持たない構成では鍵をバンドル内に置くほかなく、暗号化が実効性を持たないためです。詳細な理由と代替の管理策は 5.3 を参照してください
- 通信は HTTPS により暗号化されます
- 端末紛失・盗難時の保護は、OS のストレージ暗号化と画面ロックに依存します

### 8.4 個人情報上の留意点

- 患者情報専用の入力欄はなし
- 写真に個人情報が写り込む運用リスクは残る
- 保存済みラウンドや写真は端末ブラウザの `localStorage` に残る
- 共用端末では、ブラウザのサイトデータ削除により保存内容を消去できる
- 担当者名は入力必須のため、端末内には職員氏名が保存される
- 担当者が共有・保存する `.docx` にはラウンドデータが同梱されるため、ファイルの配布範囲は施設の運用で管理する必要がある（8.1）
- 統合ページは読み込んだデータを保存しないため、統合作業に使った PC には記録が残らない（統合結果として保存した `.docx` を除く）

### 8.5 認証

- アプリ自身はログイン機能を持ちません
- アクセス制限が必要な場合は、配信環境側で制御します

## 9. ホスティング要件

### 9.1 配信条件

## 11. 既知の実装前提

- 保存済みデータは同一ブラウザ内でのみ利用可能
- `localStorage` 容量に依存するため、大量の高解像度写真保存には限界がある
- ファイル共有はブラウザ実装差異の影響を受ける
- `.docx` のみ対応し、PDF 生成機能は未実装
- 保存データはアプリ独自には暗号化しない
- 1回のラウンドを複数端末でリアルタイムに共同記録する機能は未実装（部署ごとに記録した報告書を後からまとめる統合機能は 6.8）
- 統合ページは PC ブラウザでの利用を前提としており、部署数が多いと Word の表の列が狭くなり読みにくくなる（表は用紙幅に収める）
